PHARMACY POS + INVENTORY MANAGEMENT SAAS
ARCHITECTURE SPECIFICATION - STEP 1

================================================================================
EXECUTIVE SUMMARY
================================================================================

This is a production-ready architecture for a multi-tenant Pharmacy POS + Inventory Management SaaS.

CORE DESIGN PRINCIPLES:
- True multi-tenancy with database-level isolation (PostgreSQL Row-Level Security)
- Immutable audit trails for all financial transactions
- FEFO (First Expiry, First Out) built into inventory logic
- Role-based access control (RBAC) with granular permissions
- Atomic transactions for all critical operations
- Scalable from single-branch to multi-branch chains

================================================================================
MULTI-TENANCY ARCHITECTURE
================================================================================

STRATEGY: Shared Database + Row-Level Security (RLS)

WHY THIS APPROACH:
- Simpler operational management than database-per-tenant
- Cost efficient for small to medium organizations
- Database-level isolation prevents accidental data leakage
- Easier to implement organization-wide reports

IMPLEMENTATION:
1. Every table includes organization_id foreign key
2. PostgreSQL RLS policies enforce isolation at database level
3. Backend middleware sets tenant context (SET app.current_organization_id)
4. Query filtering adds secondary layer (WHERE organization_id = $1)

SECURITY LAYERS:
- Database: RLS Policy (prevents SQL injection)
- Application: Middleware (enforces org_id)
- Application: Query Filters (prevents accidental leakage)
- API: Authentication (prevents unauthorized access)

ROLE HIERARCHY:

  └─ Full access to all organizations

  └─ Full access to organization, all branches

  └─ Full access to assigned branch(es)

  └─ Medicine management, inventory, approve returns

  └─ POS only (create sales, receive payments)

  └─ Inventory management, stock transfers, purchases

ACCOUNTANT (Organization-wide)
  └─ Financial reports, payments, no transaction modification

RBAC TABLES:
- users: Global user records
- organization_users: User membership in organizations
- roles: System roles (global) + custom roles (per org)
- permissions: Global permission list
- role_permissions: Role -> Permission mapping
- user_roles: User -> Role assignment (scoped to organization)
- user_branch_access: User -> Branch access

RBAC ENFORCEMENT:
- Backend middleware checks permissions before executing actions
- Never trust frontend permissions
- All API endpoints require permission check

================================================================================
BATCH & EXPIRY & FEFO ARCHITECTURE
================================================================================

CORE PRINCIPLE: Separate Medicine from Batch

MEDICINE: Product (Paracetamol 500mg)
BATCH: Specific production batch of that medicine

Example:
Medicine: Paracetamol 500mg
├── Batch A (ABC123, Expiry: 2027-01-01, Qty: 500)
├── Batch B (XYZ456, Expiry: 2028-05-01, Qty: 800)
└── Batch C (DEF789, Expiry: 2026-12-15, Qty: 300)

FEFO ALGORITHM (First Expiry, First Out):
When selling a medicine:
1. Find all non-expired batches of that medicine in the branch
2. Sort by expiry date (earliest first)
3. Use earliest-expiring batch first
4. If insufficient quantity, continue to next batch
5. Never sell expired stock

Example:
- Need 600 units
- Batch C: 300 units (Expiry: 2026-12-15) - USE FIRST
- Batch A: 300 units (Expiry: 2027-01-01) - USE SECOND
- Total allocated: 600 units (from 2 batches)

EXPIRY TRACKING:
- Get expiring soon (30 days): Alert pharmacist
- Get expired stock: Write-off and create EXPIRY movement

================================================================================
INVENTORY ARCHITECTURE
================================================================================

CORE PRINCIPLE: Immutable Audit Trail

Every stock change creates an inventory_movement record.
Stock is never silently modified.

STOCK CALCULATION STRATEGY: Hybrid Approach

STORED BALANCE (inventory.quantity_on_hand):
- Fast queries for current stock
- Updated with each movement

AUDIT TRAIL (inventory_movements):
- Verify balance and detect discrepancies
- Immutable record of all changes

RECONCILIATION:
- Periodic stock counts ensure accuracy
- Detect and log discrepancies

MOVEMENT TYPES:
- OPENING_STOCK: Initial stock entry
- PURCHASE: Purchase completion
- SALE: Sale completion
- SALE_RETURN: Customer return
- PURCHASE_RETURN: Return to supplier
- TRANSFER_IN: Receive from another branch
- TRANSFER_OUT: Send to another branch
- ADJUSTMENT: Stock count adjustment
- DAMAGE: Damaged stock
- EXPIRY: Expired stock write-off

INVENTORY QUERIES:
1. Get available stock for sale (FEFO):
   - Find non-expired batches
   - Sort by expiry date
   - Check quantity_available (on_hand - reserved)

2. Get stock by branch:
   - Total quantity per medicine per branch
   - Nearest expiry date

3. Get low stock alerts:
   - Current stock < reorder_level
   - Trigger purchase request

4. Get expiring soon:
   - Expiry date between today and 30 days
   - Alert for FEFO priority

================================================================================
PURCHASE ARCHITECTURE
================================================================================

PURCHASE WORKFLOW:
1. DRAFT: Create purchase record, add items
2. COMPLETED: Create batches, increase inventory, update supplier balance
3. CANCELLED: Mark as cancelled, no stock changes

PURCHASE TRANSACTION (Atomic):
1. Get purchase record
2. Validate status is DRAFT
3. For each purchase item:
   a. Create or update batch
   b. Create or update inventory
   c. Create inventory movement
4. Update purchase status to COMPLETED
5. Update supplier balance
6. Record payment (optional)

CRITICAL CONSTRAINTS:
- Purchase number must be unique per organization
- Batch number must be unique per organization
- All operations must be atomic (all succeed or all fail)
- Supplier balance must be updated
- Inventory movements must be immutable

================================================================================
POS/SALES ARCHITECTURE
================================================================================

SALE WORKFLOW:
1. DRAFT: Build cart, add items, apply discounts
2. COMPLETED: Validate stock (FEFO), create sale, decrease inventory, record payment
3. CANCELLED: Restore stock, create reverse movements
4. RETURNED: Create sale_return, restore stock, adjust profit

SALE TRANSACTION (Atomic):
1. Get sale record and items
2. For each item:
   a. Get FEFO batches (sorted by expiry)
   b. Validate stock availability
   c. Allocate quantity to batches
3. Create sale record with calculated profit
4. Create sale items (one per batch used)
5. Decrease inventory (create SALE movements)
6. Record payment
7. Create audit log entry

PROFIT CALCULATION:
Profit = Revenue - Cost of Goods Sold
Revenue = (Quantity * Unit Price) - Discount + Tax
COGS = Sum of (Quantity * Batch Purchase Price) for each batch used

COST PRESERVATION:
- Store cost_price in sale_items (from batch.purchase_price)
- Preserve historical cost even if batch price changes
- Enables accurate profit calculation

================================================================================
RETURN ARCHITECTURE
================================================================================

SALE RETURN:
1. Customer returns medicine
2. Create sale_return record
3. Restore stock (create SALE_RETURN movement)
4. Reverse profit calculation
5. Refund payment

PURCHASE RETURN:
1. Return medicine to supplier
2. Create purchase_return record
3. Decrease inventory (create PURCHASE_RETURN movement)
4. Reduce supplier balance
5. Record payment (credit)

RETURNS AFFECT:
- Inventory (restored)
- Batch quantity (increased)
- Revenue (reversed)
- Cost (reversed)
- Profit (reversed)
- Supplier/Customer balance (reversed)

================================================================================
STOCK TRANSFER ARCHITECTURE
================================================================================

STOCK TRANSFER WORKFLOW:
1. REQUESTED: Branch A requests transfer to Branch B
2. APPROVED: Branch Manager approves
3. DISPATCHED: Branch A sends stock
4. RECEIVED: Branch B receives stock
5. CANCELLED: Transfer cancelled

STOCK TRANSFER TRANSACTION (Atomic):
1. Validate stock in from_branch
2. Create TRANSFER_OUT movement in from_branch
3. Create TRANSFER_IN movement in to_branch
4. Update inventory in both branches
5. Update transfer status

CRITICAL CONSTRAINT:
- Stock must not be duplicated during transfer
- From branch loses stock immediately (TRANSFER_OUT)
- To branch gains stock on receipt (TRANSFER_IN)

================================================================================
PROFIT CALCULATION ARCHITECTURE
================================================================================

PROFIT CALCULATION FORMULA:
Profit = Total Revenue - Total Cost of Goods Sold

REVENUE CALCULATION:
Revenue = (Quantity * Unit Price) - Line Discount + Line Tax

COGS CALCULATION:
For each sale item:
  COGS = Quantity * Cost Price (from batch at time of sale)

COST PRESERVATION:
- Store cost_price in sale_items at time of sale
- Cost price = batch.purchase_price (historical)
- Enables accurate profit even if batch price changes later

PROFIT CALCULATION EXAMPLE:
Item 1:
  Quantity: 10 units
  Unit Price: 50 (Retail)
  Cost Price: 30 (Batch purchase price)
  Line Discount: 5
  Line Tax: 7.5
  Revenue: (10 * 50) - 5 + 7.5 = 502.5
  COGS: 10 * 30 = 300
  Profit: 502.5 - 300 = 202.5

PROFIT ADJUSTMENTS:
- Sale Return: Reverse profit
- Purchase Return: Adjust COGS
- Discount: Reduce revenue
- Tax: Increase revenue

AUDIT LOG ARCHITECTURE
================================================================================

IMMUTABLE AUDIT TRAIL:
Every important action is logged:
- Login/Logout
- Medicine creation/update
- Purchase completion
- Sale completion
- Sale return
- Purchase return
- Stock adjustment
- Stock transfer
- User creation
- Permission changes
- Settings changes

AUDIT LOG FIELDS:
- organization_id: Which organization
- branch_id: Which branch (if applicable)
- user_id: Who performed action
- action: What action (create_medicine, complete_sale, etc.)
- entity_type: What entity (medicine, sale, purchase, etc.)
- entity_id: ID of entity affected
- old_values: Previous values (JSONB)
- new_values: New values (JSONB)
- ip_address: Source IP
- user_agent: Browser/client info
- status: success or error
- error_message: If failed
- created_at: When it happened

AUDIT USES:
- Regulatory compliance
- Fraud detection
- Troubleshooting
- Historical analysis
- Data recovery

================================================================================
SECURITY ARCHITECTURE
================================================================================

PROTECTION AGAINST:

1. SQL INJECTION:
   - Use parameterized queries (pg library)
   - Input validation with Zod
   - Never concatenate user input into SQL

2. XSS (Cross-Site Scripting):
   - React escapes JSX by default
   - Sanitize user input before rendering
   - Use Content Security Policy (CSP) headers

3. CSRF (Cross-Site Request Forgery):
   - Use SameSite cookie flag
   - Verify Origin header
   - Use CSRF tokens for state-changing requests

4. UNAUTHORIZED API ACCESS:
   - Require JWT token for all protected endpoints
   - Verify token expiry and signature
   - Implement refresh token rotation

5. TENANT DATA LEAKAGE:
   - RLS policies at database level
   - Middleware enforces organization_id
   - Query filtering adds secondary layer
   - Audit logs track cross-org access attempts

6. PRIVILEGE ESCALATION:
   - RBAC enforced at API layer
   - Never trust frontend permissions
   - Verify user roles in backend
   - Audit all permission changes

7. BRUTE FORCE LOGIN:
   - Rate limit login attempts
   - Lock account after N failed attempts
   - Implement CAPTCHA after failures

8. INSECURE FILE UPLOADS:
   - Validate file type (whitelist)
   - Check file size limits
   - Scan for malware
   - Store in secure location

9. FINANCIAL RECORD MANIPULATION:
   - All transactions atomic (all succeed or all fail)
   - Immutable audit logs
   - Digital signatures for important records
   - Regular reconciliation

================================================================================
TRANSACTION/CONCURRENCY STRATEGY
================================================================================

CRITICAL TRANSACTIONS (Must be atomic):

1. COMPLETE PURCHASE:
   - Create/update batch
   - Create/update inventory
   - Create inventory movement
   - Update purchase status
   - Update supplier balance
   All succeed or all fail

2. COMPLETE SALE:
   - Validate stock (FEFO)
   - Allocate batches
   - Create sale record
   - Create sale items
   - Decrease inventory
   - Create inventory movements
   - Calculate profit
   - Record payment
   All succeed or all fail

3. SALE RETURN:
   - Create sale_return record
   - Restore inventory
   - Create reverse movements
   - Reverse profit
   All succeed or all fail

4. PURCHASE RETURN:
   - Create purchase_return record
   - Decrease inventory
   - Create reverse movements
   - Reduce supplier balance{
