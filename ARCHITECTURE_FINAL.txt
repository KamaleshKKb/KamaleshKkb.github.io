CONCURRENCY CONTROL (continued)
================================================================================

PREVENT RACE CONDITIONS:
- Use database transactions for all critical operations
- Implement optimistic locking (version numbers) for frequently updated records
- Use row-level locks for inventory updates
- Queue concurrent sales for same batch

OVERSELLING PREVENTION:
- Lock batch row during sale completion
- Check available quantity before allocation
- Allocate and deduct atomically
- Create inventory movement immediately

DUPLICATE PREVENTION:
- Unique constraint on invoice_number per organization
- Unique constraint on batch_number per organization
- Unique constraint on purchase_number per organization
- Unique constraint on return_number per organization

NEGATIVE STOCK PREVENTION:
- CHECK constraint: quantity_on_hand >= 0
- Validate stock before deduction
- Reverse movements on cancellation
- Reconciliation catches discrepancies

TESTING STRATEGY
================================================================================

CRITICAL TEST AREAS:

1. TENANT ISOLATION:
   - User from Org A cannot access Org B data
   - RLS policies enforced at database level
   - Query filters prevent leakage
   - Audit logs track violations

2. RBAC:
   - CASHIER cannot create medicines
   - PHARMACIST can create medicines
   - ACCOUNTANT cannot create sales
   - SUPER_ADMIN can access all orgs
   - Permission denied returns 403

3. FEFO:
   - Earliest expiry batch used first
   - Expired batches never sold
   - Quantity allocation correct
   - Cost price from correct batch

4. EXPIRY PREVENTION:
   - Cannot sell expired stock
   - Expiring soon alerts triggered
   - Expired stock identified for write-off
   - EXPIRY movements created

5. STOCK CALCULATION:
   - Inventory matches movements
   - Stock never negative
   - Reconciliation catches discrepancies
   - Transfers don't duplicate stock

6. PURCHASE TRANSACTION:
   - Batch created on completion
   - Inventory increased correctly
   - Movement recorded
   - Supplier balance updated
   - All succeed or all fail

7. SALE TRANSACTION:
   - Stock validated before sale
   - FEFO batches allocated
   - Inventory decreased correctly
   - Movements recorded
   - Profit calculated correctly
   - Payment recorded
   - All succeed or all fail

8. SALE RETURN:
   - Stock restored correctly
   - Profit reversed
   - Movements reversed
   - Payment reversed
   - All succeed or all fail

9. PURCHASE RETURN:
   - Stock decreased correctly
   - Supplier balance reduced
   - Movements created
   - All succeed or all fail

10. STOCK TRANSFER:
    - From branch loses stock (TRANSFER_OUT)
    - To branch gains stock (TRANSFER_IN)
    - No duplication
    - Status transitions valid

11. CONCURRENT SALES:
    - Two concurrent sales don't oversell
    - Both succeed if stock available
    - One fails if insufficient
    - Stock consistent

12. NEGATIVE STOCK PREVENTION:
    - Cannot reduce stock below 0
    - Constraint enforced
    - Error returned to user

TEST TYPES:
- Unit tests: FEFO algorithm, profit calculation, validators
- Integration tests: Complete sales, purchases, returns
- E2E tests: Full workflow from POS to reports
- Load tests: Concurrent sales, high transaction volume
- Security tests: Tenant isolation, RBAC, SQL injection

================================================================================
POTENTIAL ARCHITECTURAL RISKS
================================================================================

RISK 1: DATABASE PERFORMANCE AT SCALE
Problem: Large organizations with millions of transactions
Mitigation:
- Implement table partitioning by organization and date
- Create appropriate indexes
- Use materialized views for reports
- Implement caching layer
- Monitor query performance

RISK 2: TENANT DATA LEAKAGE
Problem: RLS policies misconfigured or bypassed
Mitigation:
- Multiple isolation layers (RLS, middleware, query filtering)
- Regular security audits
- Penetration testing
- Audit logs for all cross-org access
- Automated compliance tests

RISK 3: FINANCIAL DATA INTEGRITY
Problem: Concurrent transactions causing inconsistency
Mitigation:
- All critical operations in atomic transactions
- Optimistic locking for frequently updated records
- Regular reconciliation
- Audit logs for all changes
- Digital signatures for important records

RISK 4: OVERSELLING
Problem: Two concurrent sales selling same stock
Mitigation:
- Lock batch row during sale
- Atomic stock deduction
- Inventory movement immediately
- Reconciliation catches issues

RISK 5: INCORRECT PROFIT CALCULATION
Problem: COGS not calculated correctly
Mitigation:
- Store cost_price in sale_items
- Preserve historical costs
- Automated profit calculation
- Regular audits and reconciliation

RISK 6: FEFO NOT FOLLOWED
Problem: Wrong batch sold first
Mitigation:
- FEFO algorithm in backend
- Batch allocation validated
- Audit logs for batch usage
- Regular inventory audits

RISK 7: EXPIRED STOCK SOLD
Problem: Expired medicines in sale
Mitigation:
- CHECK constraint: expiry_date > CURRENT_DATE
- FEFO algorithm filters expired
- Expiry alerts
- Regular inventory audits

RISK 8: SCALABILITY ISSUES
Problem: System slow with large organizations
Mitigation:
- Horizontal scaling architecture
- Database optimization
- Caching layer
- Load testing
- Performance monitoring

RISK 9: BACKUP AND RECOVERY
Problem: Data loss due to corruption or disaster
Mitigation:
- Automated daily backups
- Backup encryption
- Backup testing (restore drills)
- Disaster recovery plan
- Geographic redundancy

RISK 10: COMPLIANCE VIOLATIONS
Problem: Regulatory non-compliance
Mitigation:
- Audit logs for compliance
- Data retention policies
- GDPR/CCPA compliance
- Regular compliance audits
- Legal review
